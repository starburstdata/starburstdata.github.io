Privileges#

A privilege is the right to perform an action on an entity. You grant privileges to roles, and users get privileges through the roles that they hold. This page describes how to grant privileges, and it lists the privileges that you can grant in the Control Plane UI.

Each privilege applies to one kind of entity. Account privileges apply to the Control Plane as a whole. Data privileges apply to catalogs, schemas, tables, columns, functions, and storage locations.

Grant privileges#

You grant privileges to a role on its Privileges tab. To grant privileges based on tags, use policies.

Add privileges#

  1. In the Control Plane UI, go to Access > Roles and privileges, and select the role.

  2. On the Privileges tab, click Add privilege.

  3. Select the tab for the kind of privilege: Data, Account, Location, or Function. On the Data tab, select a catalog, schema, table, or column in Scope. On the Location tab, enter the storage location.

  4. Select the privileges to grant, and click Save privileges.

Change a privilege#

  1. On the Privileges tab, search for the catalog and expand the tree to the table.

  2. Open the table’s menu and select Modify privileges.

  3. Change the settings for the privilege and save your changes.

Allow and deny#

Each grant either allows or denies a privilege. A new grant allows the privilege. To block a data privilege, open Modify privileges and set Allow or deny? to DENY. A DENY always overrides an allow. You can’t deny account privileges, such as Create catalog.

Grant option#

To let a role grant a privilege to other roles, select Grant to others? for the privilege in Modify privileges. You can’t deny a privilege that has the grant option. While the option is selected, you can’t change the Allow or deny? setting.

Grant privileges with SQL#

You can also grant, deny, and revoke privileges with SQL. Specify the privilege, the entity kind, and the entity name:

GRANT CREATE_SCHEMA ON CATALOG example TO ROLE analyst;
GRANT SELECT ON TABLE example.sales.customers TO ROLE analyst WITH GRANT OPTION;
DENY SELECT ON TABLE example.sales.customers TO ROLE contractor;
REVOKE SELECT ON TABLE example.sales.customers FROM ROLE analyst;

For account privileges, use MY ACCOUNT as the entity. For location privileges, put the storage location in double quotes:

GRANT CREATE_CATALOG ON MY ACCOUNT TO ROLE data_admin;
GRANT CREATE_SQL ON LOCATION "s3://example-bucket/data/*" TO ROLE data_admin;

View privileges#

To query a view, a role needs the Select from table privilege on the view. What else it needs depends on the security mode of the view:

  • A SECURITY INVOKER view runs with the privileges of the role that queries it. That role also needs Select from table on the tables that the view reads from.

  • A SECURITY DEFINER view runs with the privileges of the role that owns the view. The owning role needs Select from table with the grant option on the tables that the view reads from, unless the querying role is the owning role or holds it. This keeps a role from sharing access to tables through a view when it can’t grant that access directly.

A SECURITY DEFINER view that was created outside STAC, such as in a delegated catalog, has no STAC owner and fails until you set one:

ALTER VIEW example.sales.monthly_summary SET AUTHORIZATION ROLE analyst;

Location privileges#

You need the Create schema and table in location privilege to set an explicit location when you create a schema or table in any catalog, governed or delegated. This applies to all roles, including accountadmin. Schemas and tables that you create without an explicit location don’t need it.

Location privileges apply to a storage location path that starts with s3://, gs://, abfs://, or abfss:// and ends with /*, such as s3://example-bucket/data/*. You can’t deny location privileges.

If the Control Plane uses a MySQL database, the storage location in a location privilege can have at most 192 characters.
