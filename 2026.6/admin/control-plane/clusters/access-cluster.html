Access a managed cluster#

Control plane exposes each cluster that it manages under the path /clusters/<cluster-name>/ of the control plane URL, and forwards requests to that path to the named cluster. Use this path to open the web UI of a managed cluster or call its REST API. For example, you can manage built-in access control roles with /api/v1/biac/roles.

A cluster in managed mode only accepts users that control plane authenticates. You can’t sign in to the cluster directly, with its web UI or with a REST client, using password, OAuth 2.0, or certificate authentication. Instead, sign in through control plane, and reach the cluster through /clusters/<cluster-name>/.

The forwarded paths are the paths of the cluster itself. For example, https://control-plane.example.com/clusters/sales/api/v1/biac/roles reaches /api/v1/biac/roles on the sales cluster.

Requirements#

  • The cluster runs in managed mode. See Connect a cluster to control plane.

  • Cluster authentication is turned on in control plane, with gateway.clusters.authentication.enabled=true, and control plane uses tag-based routing. See Configure cluster authentication.

  • <cluster-name> is the name of the cluster in control plane, which matches the node.environment property of the cluster.

Open the web UI of a cluster#

Open the cluster from the cluster list in the control plane UI, or go to the following address:

https://<control-plane>/clusters/<cluster-name>/ui/insights/

If you aren’t signed in, the sign-in page of the cluster redirects you to the sign-in page of control plane. After you sign in, control plane opens its home page, not the cluster page that you asked for. Open the cluster page again from the cluster list.

The web UI of the cluster runs as the user that is signed in to control plane. The sign-in methods of the cluster web UI aren’t available in managed mode, so you sign in and out through control plane.

Call the REST API of a cluster#

Send the request to control plane, with the /clusters/<cluster-name> prefix, and authenticate to control plane with any authentication type that is configured for it. Control plane accepts credentials in the Authorization header, so scripts and other non-interactive clients can use this path.

For example, with password authentication configured on control plane:

curl -u <username> \
  https://control-plane.example.com/clusters/sales/api/v1/biac/roles

Control plane authenticates the request and forwards it to the cluster as the signed-in user. Control plane doesn’t pass the Authorization header or the cookies of the client on to the cluster. It sends its own credential instead. Access control on the cluster applies to the signed-in user as usual.

If the credentials are invalid, control plane rejects the request and doesn’t forward it.

Control plane forwards all HTTP methods that the REST API uses: GET, POST, PUT, PATCH, DELETE, and HEAD.

Queries that you submit through /clusters/<cluster-name>/v1/statement run on the named cluster. If the control plane statement queue is turned on, these queries are queued for that cluster. See Statements that name a cluster.

Public endpoints#

Endpoints that don’t need authentication on a cluster, such as /v1/info and /v1/status, don’t need it through control plane either. Control plane forwards a request without credentials to the cluster as is, without a control plane credential, and the cluster answers it:

curl https://control-plane.example.com/clusters/sales/v1/info

A request without credentials to an endpoint that needs authentication, such as /api/v1/biac/roles or /v1/statement, fails with 401 Unauthorized.

Errors when you connect to the cluster directly#

A managed cluster expects a credential that control plane issues. When a request reaches the cluster without one, for example because it was sent to the cluster URL instead of through control plane, the cluster returns the following error:

HTTP 401 Unauthorized
WWW-Authenticate: Galaxy
Galaxy token is required

The Galaxy token is the credential that control plane issues. The error means that the request didn’t come through control plane as an authenticated user. It doesn’t mean that the token of the client was wrong. To fix it, send the request to https://<control-plane>/clusters/<cluster-name>/... with control plane credentials.

A query that you submit with POST /v1/statement directly to the cluster fails with the following error:

HTTP 401 Unauthorized
WWW-Authenticate: Galaxy
Deprecated API

A managed cluster only accepts queries that control plane submits. Despite the Deprecated API message, the API isn’t deprecated. Submit queries through control plane, at https://<control-plane>/clusters/<cluster-name>/v1/statement, or with the control plane URL as the server address of the client.

The cluster web UI doesn’t show these errors when you open it through control plane. It redirects you to the sign-in page of control plane instead.

Troubleshooting#

  • Galaxy token is required through control plane while you are signed in: Check that gateway.clusters.authentication.enabled is true on control plane. When it is turned off, control plane forwards requests without issuing a credential.

  • Cluster name mismatch, Expected sub claim ...: Check that the name of the cluster in control plane matches its node.environment property.

  • Issuer mismatch, Expected iss claim ...: Check that gateway.clusters.authentication.issuer matches the deployment.manager.uri property of the cluster, or its http-server.authentication.managed.issuer property if it is set.

  • REST automation that worked before the cluster was managed: Change the base URL from the cluster URL to https://<control-plane>/clusters/<cluster-name>, and authenticate to control plane instead of the cluster.
