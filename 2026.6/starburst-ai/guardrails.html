Starburst AI Guardrails#

Guardrails are policies that govern how AIDA behaves: what it refuses, how it handles oversized inputs, which topics it engages with, and which content it accepts and returns. They apply to all AI models and agents on the cluster.

An administrator configures guardrails once, at the cluster level, and SEP applies them on every request. Prompt limiting validates the size of each message before it reaches the model. Agent protection, data product protection, and topic filtering adjust the model’s instructions for each turn. Content scanning checks questions, responses, and external MCP tool results with an Amazon Bedrock guardrail that runs outside the model. Agent protection, data product protection, and prompt limiting are on by default. You can turn off any protection that is too strict for your environment.

Guardrails govern how AIDA behaves. They do not replace your existing security controls such as Database permissions, row-level security, column masking, and data product access which govern the data AIDA can reach.

Configuration#

Only users in the sysadmin role can view and edit guardrails. To edit the default guardrails, follow these steps:

  1. Click AI > Guardrails in the Starburst Enterprise web UI navigation menu.

  2. On the Guardrails page, locate the Default policy. This policy applies to all AI models and agents on the cluster.

  3. In the Default row, click the more_vert options menu, then select Edit.

  4. In the Edit default guardrails dialog, select or clear the checkboxes for the protections you want, then click Save. If you turn on content scanning or change its settings, click Test connection before you save. For more information, see Configure content scanning.

The following table lists the configurable guardrails and their default state:

Note

Guardrail settings are cluster-wide and global. One configuration applies to every data product, model, chat session, and user. There are currently no per-data-product, per-user, or per-model overrides.

You can turn off and completely hide the Guardrails feature. set the following property to false in your coordinator configuration file:

ai.agent.guardrails.enabled=false

When set to false, guardrails in AIDA are completely turned off. Additionally, the Guardrails page is hidden from all users. The property defaults to true.

Configurable guardrails#

The following sections detail each configurable guardrail protection.

Agent protection#

When on, AIDA resists two categories of misuse:

  • Configuration extraction: AIDA refuses requests to reveal its instructions, list its rules, translate them, or document them through role-play.

  • Indirect prompt injection: AIDA treats command-like text found in tool results or query rows as data, not as directives.

When turned off, AIDA uses a friendlier baseline. It might describe its own setup and is more likely to follow instructions embedded in tool results.

Data product protection#

Every chat session is scoped to one data product. When on, AIDA treats that scope as a hard boundary and:

  • Refuses to run SQL against tables outside the data product, even if the user has direct Trino permissions for them.

  • Refuses to display or template out-of-scope SQL.

  • Refuses to display scope-expansion framings such as hypothetically, just this once, or as an admin.

  • Refuses to use built-in tools as a general calculator, translator, or trivia engine.

External Model Context Protocol (MCP) tools attached to the session are unaffected and remain available. When turned off, AIDA receives the data product’s name and description as context only, and runs any SELECT query the user has permission for.

Prompt limiting#

When on, SEP rejects any message longer than the configured limit before it reaches the model. No tokens are consumed, and the user sees the following error:

Your request was too long. Please rephrase your question with less detail.

The limit ranges from 1 to 1,000,000 characters. The default is 50,000 characters.

When off, SEP enforces no length limit. The model’s own context window still applies.

Topic filtering#

When on, you provide a list of topic keywords or phrases, and AIDA refuses any request that touches one. The filter is semantic. For example, adding comedy refuses tell me a joke as well as the literal word.

Topic filtering suits organizations that want a narrowly focused analytics agent, such as a financial-services deployment that should not offer investment advice.

Topic filtering is off by default. No topic filter is applied.

Content scanning#

Content scanning sends AIDA’s input and output to an Amazon Bedrock guardrail that you create and manage in your own AWS account. Other guardrails adjust the model’s instructions and depend on the model to follow them. Content scanning runs outside the model, so a request that persuades the model to ignore its instructions does not bypass it.

You define the policies in Amazon Bedrock, so you can apply the same policies to AIDA that your organization uses for other AI applications, including:

  • Content filters for harmful content and prompt attacks.

  • Denied topics.

  • Word filters.

  • Sensitive information filters that block or mask personally identifiable information (PII) and custom patterns.

When on, SEP scans the following content:

  • Questions: SEP scans each question that a user submits in the AIDA chat before the model receives it.

  • Responses: SEP holds each complete model response and scans it before the user sees it.

  • External MCP tool results: SEP scans the results that external MCP servers return, including error messages, before the model receives them.

Each scan has one of the following outcomes:

  • Allowed: The content passes unchanged.

  • Masked: The guardrail masks sensitive details, such as a credit card number. Only the masked text reaches the model, the user, and the chat history. When the guardrail masks part of a question, the question in the chat updates to show the masked text. When the guardrail masks an external MCP tool result, the model receives the masked result as plain text, which might no longer be valid JSON.

  • Blocked: SEP replaces the content with a fixed message. A blocked question never reaches the model.

  • Error: The scan times out, Amazon Bedrock returns an error or an unexpected response, or SEP cannot use the trusted connection. SEP refuses the content and shows a fixed error message.

When the guardrail blocks a response, the turn completes with the refusal message. When content scanning cannot check a response, the turn ends as failed. Callers of Starburst AI via MCP receive a failed turn instead of an answer.

Important

Content scanning fails closed. If Amazon Bedrock is unavailable or the trusted connection’s credentials stop working, AIDA declines questions and withholds responses until you resolve the problem or turn off content scanning.

While content scanning is on, AIDA does not stream responses as the model writes them. The chat shows an activity indicator, such as Checking response with guardrails..., and then shows the complete response.

Content scanning does not cover every AIDA entry point or tool. For details, see Limitations.

Requirements#

To use content scanning, you need:

  • An Amazon Bedrock guardrail, and its guardrail ID and version. For more information, read Create your guardrail in the AWS documentation.

  • A guardrail without an Automated Reasoning checks policy. SEP does not support Automated Reasoning checks, and every scan that such a policy intervenes on fails closed.

  • An Amazon Bedrock trusted connection in the same AWS region as the guardrail. You can select a connection that your Amazon Bedrock AI models already use, or create a separate one.

  • AWS credentials for the trusted connection that have the bedrock:ApplyGuardrail permission for the guardrail. For an example policy, read Set up permissions to use Amazon Bedrock Guardrails in the AWS documentation. If the connection authenticates with an AWS IAM role, the base credentials must be able to assume that role.

Contextual grounding checks have no effect. SEP does not send Amazon Bedrock a reference source or a query, so Amazon Bedrock skips the check.

Content scanning sends question, response, and tool result text to Amazon Bedrock in the trusted connection’s region. Choose a region that meets your data residency requirements. Amazon Bedrock bills guardrail usage to your AWS account, and a single AIDA turn can run several scans. For example, each external MCP tool result can take up to four scans.

Note

Test connection on the trusted connection checks the bedrock:ListFoundationModels permission, not bedrock:ApplyGuardrail. A connection can pass its own test and still fail the content scanning test.

Configure content scanning#

  1. Open the Edit default guardrails dialog as described in Configuration.

  2. Select Content scanning.

  3. Enter the following details:

    • Trusted connection to Amazon Bedrock: Select the trusted connection to use. The list shows only Amazon Bedrock trusted connections.

    • Guardrail ID: Enter the ID of your Amazon Bedrock guardrail.

    • Guardrail version: Enter DRAFT or a version number of up to 8 digits, such as 1.

    • Request timeout (seconds): Enter the maximum time SEP waits for each scan, including the time to create the Amazon Bedrock client and resolve the trusted connection’s secret references. The value ranges from 1 to 60 seconds. The default is 5 seconds. Each external MCP tool result can take up to four scans, so a slow guardrail can add up to four times this value to an external MCP tool call.

    • Scan remote MCP tool results: Select to scan results that external MCP servers return. This option is selected by default.

  4. Click Test connection. SEP sends a fixed test string to the guardrail and shows Successfully connected when the test passes.

  5. Click Save.

When you turn on content scanning, or change the trusted connection, guardrail ID, guardrail version, or request timeout, the dialog shows Test connection in place of Save until the current settings pass the test. This check prevents a mistyped guardrail ID from blocking every chat. If the saved Amazon Bedrock settings are unchanged, the dialog shows both buttons, and you can save other changes without a new test.

Tip

Use a numbered guardrail version in production. The DRAFT version is the guardrail’s working draft, which changes each time you edit the guardrail in Amazon Bedrock.

Caution

When you clear Scan remote MCP tool results, external MCP tool results reach the model without an independent check. Keep this option selected unless you trust every external MCP server attached to AIDA.

While content scanning is on, you cannot delete its trusted connection or change the connection’s type. When you turn off content scanning, SEP keeps the guardrail ID, version, timeout, and MCP setting, but clears the trusted connection selection so that you can delete the connection. Select the trusted connection again when you turn content scanning back on.

Content scanning messages#

SEP shows its own fixed messages instead of the blocked messaging configured in your Amazon Bedrock guardrail, and never shows Amazon Bedrock error details to users. Each message states whether content scanning declined the question or withheld the response or tool result, and why:

  • did not meet the configured content policy: The guardrail blocked the content. Review the policies in your Amazon Bedrock guardrail.

  • could not be completed: The scan failed, so SEP blocked the content. See Content scanning errors.

A declined question remains in the chat session as the placeholder This question was withheld by content scanning., followed by the message. SEP never stores the submitted text, and later turns leave it out of the model’s context.

How configuration changes affect chat sessions#

When an administrator saves a change to the guardrail settings:

  • SEP writes an audit line to the coordinator log that records the acting user and the new settings.

  • The updated settings apply to new chat sessions immediately.

  • The updated settings also apply to existing chat sessions.

Changes to Prompt limiting and Content scanning take effect immediately. SEP applies the new settings on the next message in any session. Turning on content scanning does not scan earlier messages. Content that the model received before you turned on content scanning stays in the conversation history.

Agent protection, Data product protection, and Topic filtering work by adjusting the model’s instructions on each turn. Because earlier replies remain in the conversation history, the model tends to stay consistent with what it has already said. In practice:

  • Tightening protections mid-chat works for new topics. The next question is governed by the new setting.

  • Tightening protections mid-chat does not redact earlier answers. Information already disclosed to the model stays visible, and the model might keep referring to it.

  • Relaxing protections mid-chat does not always unblock prior refusals. After AIDA refuses a class of request, it tends to keep refusing similar follow-ups.

Note

To make a setting change fully take effect, start a new chat session.

A guardrail block does not end the session; it only returns a message. The session continues in every case.

Limitations#

  • Configuration is global: One configuration applies to the entire cluster. There are currently no per-data-product, per-user, or per-model overrides.

  • Refusals are not aggregated: Individual block events appear in the chat session, but are not aggregated into a dashboard. When content scanning masks or blocks content, or cannot complete a scan, SEP writes a Content scan line to the coordinator log with the chat session ID, the outcome, and the Amazon Bedrock policy categories. The line does not include the scanned content. The outcome is ANONYMIZED for masked content, BLOCKED, or ERROR. SEP logs failed scans at the WARN level and other outcomes at the INFO level.

  • Declined questions are not in the agent interaction audit log: When content scanning declines a question, SEP does not write a row to the agent interaction audit log. The Content scan line in the coordinator log records the decline. When content scanning cannot check a response, the audit log records the turn with an ERRORED status.

  • External MCP tool results are scanned only with content scanning: When content scanning is off, or Scan remote MCP tool results is cleared, AIDA is instructed to treat external MCP tool content as untrusted data rather than as commands. No external provider evaluates the content.

  • Question scanning covers only the AIDA chat: SEP scans questions that users submit in the AIDA chat in the Starburst Enterprise web UI. SEP does not scan questions sent through the AIDA REST API, Starburst AI via MCP, or dashboard Ask, or free-text answers to AIDA’s clarifying questions. SEP still scans the model responses and external MCP tool results for these entry points.

  • Content scanning does not cover tool calls or built-in tools: SEP does not scan the arguments that the model generates for tool calls, the tool definitions that external MCP servers provide, or the results of AIDA’s built-in tools, such as SQL queries, skills, charts, and dashboards. For example, a query result table that AIDA shows in the chat is not scanned, but a model response that repeats the query data is. Use row-level security and column masking to protect sensitive data in query results.

  • Content scanning has size limits: SEP sends each question, response, or tool result to Amazon Bedrock as a single block. Content that exceeds the guardrail’s text unit limits fails closed. A guardrail with a denied topics policy has the lowest limit, about 200,000 characters. Large external MCP tool results are the most likely to exceed it.

Troubleshooting#

You can turn off each of the five configurable controls individually. The three always-on protections remain enforced.

Diagnose which guardrail is responsible#

  1. Reproduce the problem in a new chat. If the refusal does not happen, it was caused by earlier turns in the previous session, not a guardrail.

  2. If the new chat still refuses, match the symptom to a guardrail:

    • Rejected before any response: check Prompt limiting.

    • Refused to discuss its instructions or tools: check Agent protection.

    • Refused on a specific table: check Data product protection.

    • Responded with a statement that it cannot help with that topic: check Topic filtering.

    • Responded that content scanning declined the request or withheld the response or tool result: check Content scanning and the policies in your Amazon Bedrock guardrail.

  3. Turn the guardrail off, retest in a new chat session, then turn it back on. This confirms the cause without leaving the cluster with relaxed protections.

Content scanning errors#

If Test connection in the Edit default guardrails dialog shows the following error, check the guardrail ID, the guardrail version, the trusted connection’s region, and the bedrock:ApplyGuardrail permission:

Could not connect to the configured Amazon Bedrock guardrail. Check the
guardrail ID, version, and trusted connection, and that its credentials allow
bedrock:ApplyGuardrail.

SEP writes the cause of a failed test to the coordinator log in a Bedrock guardrail connection test failed line. When a scan fails during a chat, SEP writes a Content scan line with outcome=ERROR. Both lines include a reasonCode value.

After you rotate the trusted connection’s credentials, SEP uses the updated credentials within 15 minutes, without a restart.

Turn off a guardrail#

Open the Edit default guardrails dialog as described in the Configuration section, then clear the protections you want to turn off:

  • Agent protection: The agent reverts to a friendlier baseline.

  • Data product protection: The agent still receives the data product as context, but the scope is no longer a hard boundary. Any SELECT query the user has permission for runs.

  • Prompt limiting: SEP enforces no length limit. The model’s own context limit still applies.

  • Topic filtering: SEP preserves the topic list when off, so you can re-enable it later without retyping.

  • Content scanning: SEP stops scanning and keeps the guardrail ID, version, timeout, and MCP setting. SEP clears the trusted connection selection so that you can delete the connection. Select the connection again when you turn content scanning back on.

Caution

Disabling a guardrail does not unblock prior refusals. Users must start a new chat session to see the relaxed behavior. Any change is cluster-wide and immediate: turning off a guardrail to unblock one team relaxes protections for everyone until you turn it back on.

FAQ#

Q: Do guardrails replace row-level security and column masking?

A: No. Queries still run under the user’s identity, subject to the same row-level security and column-masking policies. Guardrails govern what the agent attempts; your existing controls govern what it can return.

Q: Are guardrails configured per data product, role, or user?

A: No. Guardrail settings are currently global. One configuration applies to the entire cluster, including every data product, model, chat session, and user.

Q: Should I raise the prompt limit?

A: The default of 50,000 characters is large enough for most pasted logs and short documents. Raise it only if you see legitimate messages being rejected. The maximum is 1,000,000 characters.

Q: I changed a guardrail mid-chat, but AIDA still behaves the old way. Why?

A: Most guardrail changes are sticky within an existing chat session. Agent protection, data product protection, and topic filtering adjust the agent’s instructions on each turn, but the model tends to stay consistent with its earlier replies. Start a new chat session to apply the changes. For more information, see How configuration changes affect chat sessions.

Q: Why did topic filtering refuse a question that did not seem to match?

A: Topic filtering is semantic, so it refuses any request related to a listed topic, not only exact matches. For example, a comedy topic also refuses tell me a joke. Start with narrow, specific terms, and broaden them only as needed.

Q: Does AIDA log what it blocks?

A: Individual block events appear in the chat session itself, but are not aggregated into a dashboard. When content scanning is on, SEP also logs each masked, blocked, or failed scan to the coordinator log with its outcome and Amazon Bedrock policy categories, without the scanned content. For more information, see Limitations.

Q: Do I need Amazon Bedrock AI models to use content scanning?

A: No. Content scanning needs only an Amazon Bedrock trusted connection and guardrail. It works with any AI model that AIDA uses.

Q: Why don’t users see the blocked messaging configured in my Amazon Bedrock guardrail?

A: SEP shows its own fixed messages so that refusals read consistently and no provider details reach users. To tell blocked content from a failed scan, see Content scanning messages.

Q: Why are responses slower when content scanning is on?

A: SEP holds each complete response and scans it before showing it, so the response appears all at once instead of streaming. Each external MCP tool result can also take up to four scans.
